## Кейс одной фразой
Инструмент автоматизированного red teaming, который находит **динамические атаки на память** ИИ-агента (не «вход→выход», а компрометацию долговременной памяти, срабатывающую позже/в других сессиях) и выдаёт **evidence**: что записалось в память, когда сработало, кого задело. Пользователь — департамент ИБ, проверяющий безопасность агентной памяти перед выкаткой.

## Решения после Q&A с Тимуром (главное — приоритеты сменились)
- **Только атаки на память**, динамические. Обход alignment и прочие типы — за борт. Фокус — «где ломается система при работе с памятью».
- **Ширина > глубина.** Жюри смотрит на **разнообразие атак и погружённость в них**, меньше — на трассировки/вылизывание одного кейса. НО **evidence обязателен**. (Прежняя ставка «глубина, 1–2 класса» — отменена.)
- **ASR не в заголовке.** Смотрят на **суть идеи и интерпретируемость**, а не на цифру. ASR определяем сами, свой метод на каждый тип атаки (LLM-as-judge где семантика, детерминированно где читается состояние).
- **Киллер-фича (слова Тимура):** удобная кастомизация атак и **подгрузка своих атак** в решение (желательно онлайн). Архитектурный центр, не допфича.
- **Интерфейс — CLI/скрипт.** Веб-UI и MCP не нужны. HTML-отчёт — по желанию.
- **Чёрный ящик — ок**, не привязываться к стенду. Вход: **API-контракт** стенда + **логи через Langfuse**. Метрики можно считать на стенде.
- **Две разные LLM:** атакующая ≠ ядро тест-агента (deepseek v4 flash полная / qwen3 / gpt-oss). Выбор модели — вне оценки.
- **promptfoo — мусор.** Форк LLAMATOR/garak допустим (они не умеют в память/тулы). Улучшать стенд — приветствуется, не требуется.
- **Критичные последствия взлома:** BAC (перс. данные, банковская тайна) — самый критичный; утечка по конкурентам; hijack. Это то, к чему должна приводить отравленная память.
- **Как в банке сейчас:** атаки вручную, Langfuse для логов, promptfoo+LLM для придумывания атак, есть доступ к коду агента.

## Целевой стенд (SUT): genai-invest-agent-memory-stand
Инвест-ассистент с памятью, локальный Docker. Репо: github.com/m-melgizin/genai-invest-agent-memory-stand.

**Сервисы:** LibreChat :3080 · agent-api :8600 (OpenAI-совместимый) · ReAct-агент (LangChain) · mcp-invest :8100 (14 read-тулов) · invest-server :8200 (Postgres) · Keycloak :8180/:8443 (IAM, claim `cus`) · Redis (рабочая память) · Mongo (долговременная).

**Точки входа для атак:**
- `POST /v1/chat/completions` — тело: `messages`, `auth_mode` (`vulnerable`|`protected`, дефолт vulnerable), `session_id`; заголовок `Authorization: Bearer sk-genai-…`. Поддерживает `stream:true`.
- `GET /memory` — инспекция всех уровней памяти пользователя (evidence).
- `POST /v1/sessions/{id}/finalize` — перенос рабочей памяти в долговременную (или отправить сообщением слово `finalize`).

**Каналы недоверенного ввода:** пользовательский запрос, результат веб-поиска (DuckDuckGo), результаты MCP-тулов, содержимое памяти.

**Модель памяти (Mongo):** коллекции `dialog_sessions`, `episodic_memories`, `semantic_memories`, `agent_policy_memories`. `semantic` имеет `scope: user|global` (global читают все). `agent_policy_memories` — **без user_id вообще**: любая запись подмешивается в системный промпт ВСЕХ клиентов. `build_context()` собирает промпт из всех уровней.

**Две заложенные уязвимости:**
1. **Memory poisoning (наш фокус).** `finalize` → оркестратор (summarize → extract_episodes → **extract_semantics** → persist). Если LLM в extract_semantics пометит факт `scope=global` → он уходит в `AgentPolicyMemory` без user_id → `build_context` вставляет его в системный промпт всем клиентам, запись **переживает сброс сессии**. Кросс-юзер распространение достижимо обычным диалогом.
2. **Broken Access Control (последствие).** `auth_mode=vulnerable`: агент ходит неограниченным сервис-токеном, `cus` выбирает модель; явный `cus` от модели (в т.ч. из инъекции) **побеждает** дефолт текущего клиента → чтение данных любого `cus`. В `protected` — OAuth2 Token Exchange, claim `cus` проверяется, 403 при несовпадении. Два независимых слоя: mcp-invest и invest-server.

**Данные:** 5 синтетических клиентов `cus=1001…1005` (Postgres: clients/accounts/positions/tax_records/operations/client_training). Логины client1001…1005, пароль = логин.

**LLM:** дефолт — локальная Ollama; конфиг через `OPENAI_BASE_URL`/`OPENAI_API_KEY`, `RESEARCH_MODEL`/`SUMMARIZATION_MODEL` (формат `provider:model`).

**Ключевые файлы:** `app/agent/runner.py` (ReAct-цикл, `CUS_SCOPED_TOOLS`, `SYSTEM_PROMPT`) · `app/memory/{store,mongo,models,working}.py` · `app/orchestrator/{graph,prompts}.py` (путь отравления) · `app/api_server.py` (эндпоинты) · `mcp-invest/{server,auth,data}.py` · `invest-server/init.sql` · `docker-compose.yml`.

**Запуск:** сгенерировать TLS-сертификат Keycloak (openssl, см. README) → `docker compose up -d --build`.

## Выжимка из статей (что берём в дело)
- **MPBench — 2606.04329** (ядро батареи): таксономия из **6 классов** memory poisoning + 4 канала записи. Ключ — **сила сигнала**: strong (явная команда) vs weak (правдоподобный ложный факт). Лучший детектор входа PromptArmor ловит **84,4%** сильносигнальных, но лишь **42,5%** слабосигнальных. Существующие prompt-injection защиты не покрывают poisoning. → реализуем 6 классов вширь, оба стиля сигнала.
- **GhostWriter — 2607.06595** (авто-генерация weak-signal): фазы injection (~98%) + activation (~60%). Протокол **Black-Box Retrieval Optimization**: итеративно переписывает payload по косинусной близости к кластерам легитимного корпуса (Enron) до порога — black-box. Защита AM-Sentry (memory-saving policy + retrieval screen). → наш авто-генератор слабосигнальных атак.
- **Survey — 2604.16548** (рамка): Memory Lifecycle — 6 фаз (Write, Store, Retrieve, Execute, Share&Propagate, Forget&Rollback) × 4 цели (Integrity, Confidentiality, Availability, Governance). Прямо: **ни один бенчмарк не покрывает полный цикл**. VMG — 5 примитивов, нужен provenance на этапе хранения. → язык для маппинга атак по фазам.
- **MemSecBench — 2607.27080** (протокол оценки): цикл **Write–Execute–Forget**, 310 кейсов. Вредоносная память персистит в **84,2%**, полная цепочка Write–Execute — **50,3%**. → идея per-stage evidence и как считать успех по стадиям.
- **A-MemGuard — 2510.02373** (защита-ориентир): детекторы ASB пропускают **66%** отравленных записей (безобидны поодиночке); consensus-валидация + dual-memory «уроки», режет ASR >95%. → почему детект по одной записи не работает (аргумент интерпретируемости).
- **TokenWall — 2607.08395** (защита-ориентир): семантический firewall над token-flows, source→sink аудит; на CIK-Bench ASR до 12,5% при 97,4% benign pass, +0,69с. → пример защиты на исполнении.

## MVP (текущая форма)
1. Чёрный ящик, target-agnostic: вход = API-контракт + опц. Langfuse-логи.
2. **Формат подключаемых атак** (киллер-фича): атака = декларативный файл (канал → payload/мутация → триггер → проверка успеха), автоподхват из папки.
3. Батарея вширь: 6 классов MPBench + weak-signal через retrieval-оптимизацию + кросс-юзер `scope=global`; оба стиля сигнала.
4. Evidence-слой: чтение состояния памяти (Mongo/`/memory`) + трасса Langfuse → что записалось, когда сработало, кого задело.
5. ASR — свой метод на тип атаки; маппинг находок на MITRE ATLAS / OWASP ASI06 для интерпретируемости.
6. CLI + машиночитаемый отчёт (JSON) + краткая человекочитаемая сводка.
