**Слайд 1 — Титул**

**Слайд 2 — Проблема**
Динамические атаки на память агента срабатывают позже/в других сессиях и кросс-юзер — не видны в «запрос-ответ». Текущее (ручные + promptfoo + Langfuse) память не покрывает. Цифра-якорь: входные детекторы ловят ~42% слабосигнальных отравлений (MPBench).

**Слайд 3 — Постановка задачи**
Нужен инструмент: атакует агента как чёрный ящик (API-контракт), проверяет успех по СОСТОЯНИЮ памяти + Langfuse, выдаёт интерпретируемые находки с evidence. Приоритеты после Q&A: только память · ширина>глубина · ASR не в заголовке · killer = подгрузка своих атак.

**Слайд 4 — Пользователь и ценность**
Пользователь — департамент ИБ, проверка агента перед выкаткой. Ценность: интерпретируемость + широта + evidence, а не голый ASR. Killer-фича: pluggable-формат (свои атаки без правок ядра).

**Слайд 5 — Решение / архитектура** (схема)
Поток: доставка payload (запрос/веб/вывод тула/память) → finalize → активация → evidence (Mongo/GET /memory + Langfuse) → judge → отчёт (JSON+сводка, MITRE/OWASP). Показать pluggable attack format как центр.

**Слайд 6 — Батарея атак**
6 классов MPBench + слабосигнальная авто-генерация (retrieval-оптимизация) + кросс-юзер `scope=global`; оба стиля сигнала. Врезка: карта из 12 разобранных референс-атак.

**Слайд 7 — Ключевой сценарий отравления** (схема)
`finalize → extract_semantics(scope=global) → agent_policy_memories (без user_id) → build_context → системный промпт ВСЕХ клиентов`, переживает сброс сессии. Последствие: BAC / чтение чужого `cus`.

**Слайд 9 — Риски и план до финала (07.09)**
Риски: верификация слабого сигнала (LLM-as-judge шум), схема Langfuse-логов, стоимость двух LLM. План: end-to-end одна атака → батарея на стенде → первые findings → формат отчёта с ИБ → финальные материалы.
