# Описание проекта (промежуточный этап)

## Краткая аннотация

Постоянная память агентов является новой поверхностью атаки: вредоносный ввод может сохраняться между сессиями и позже вызывать мошеннические действия или утечку данных. Например, атакующий может поместить в память агента инструкции о переводе средств или получении конфиденциальной информации, которые активируются при подходящем триггере.

## Проблематика

Банк внедряет интеллектуальных ассистентов и агентов с постоянной памятью для помощи сотрудникам и клиентам: поиска информации, обработки заявок и анализа рисков. Эти агенты запоминают контекст диалогов, цели, данные клиентов, списки разрешённых действий и т.д.

Отдел кибербезопасности должен проверять предлагаемые бизнесом решения перед выводом в прод на соответствие стандартам безопасности. Сейчас существуют автоматизированные проверки для LLM систем на вход-выход (promptfoo, garak, llamator), однако сложные агентные системы с памятью на данный момент требуют ручной проверки, которая может занимать от нескольких часов.

## Актуальная постановка задачи

Наша задача - создать инструмент, автоматизирующий пентестинг и red teaming различных компонент и механизмов памяти в агентных системах. Инструментом пользуется сотрудник кибербезопасности при оценке надежности системы: ему выдается отчет о проведенных атаках, включающий их точки входа, тактики и статистику успеха. На основе этих данных сотрудник принимает решение о митигации уязвимостей.

## Выбранное техническое решение

* Pluggable attack format (архитектурный центр): атака = декларативный файл (канал доставки → payload/мутация → триггер активации → success-check → сила сигнала). Новый файл = новая атака, без правок ядра.
* Черный ящик, target-agnostic: вход - API-контракт агента (+опц. Langfuse-логи), стенд не захардкожен.
* Батарея вширь: 6 классов memory poisoning (MPBench) + авто-генерация слабосигнальных (retrieval-оптимизация, GhostWriter) + кросс-юзер scope=global; оба стиля сигнала.
* Evidence-слой: чтение состояния памяти (Mongo / GET /memory) + трасса Langfuse → диф «до/после».
* Две разные LLM: атакующая ≠ ядро тест-агента; ASR считаем своим методом на каждый тип (LLM-as-judge для семантики, детерминированно где читается состояние). Маппинг находок на MITRE ATLAS / OWASP ASI06.
* Интерфейс - CLI + машиночитаемый отчёт (JSON) + краткая сводка.

## Уже реализованные компоненты

* Развёрнута локально мишень (стенд genai-invest-agent-memory-stand), плюс изолированная копия стенда для параллельных прогонов без взаимных помех.
* Собрана и структурирована база знаний атак: 12 разобранных публичных writeups, размеченных по каналам/классам/последствиям (docs/attack-references.md, docs/references/).
* **Работают два независимых инструмента**, атакующих одни и те же механизмы памяти — это даёт перекрёстную проверку находок:
  * **core-harness** (pluggable-формат «атака = файл»): цикл target → память → evidence → судья → отчёт, 7 attack-паков, автоподхват новых атак файлом.
  * **memred** (YAML-атаки + движок мутаций): 22 шаблона атак (21 класс) и 3 многошаговые APT-цепочки, детерминированный стадийный вердикт (внедрение → извлечение → активация → принятие), композитная метрика MSI 0–100 вместо бинарного ASR, выгрузка findings.json + SARIF 2.1.0 и матрица покрытия для импорта в ASOC.
* Проведены батареи прогонов на живом стенде с повторами (k≥3), сравнением режимов vulnerable/protected и авто-отчётами.

## Предварительные результаты

Оба инструмента подтвердили, что write-path памяти открыт практически для всех классов атак (внедрение ~100%), а различается устойчивость активации. Ключевые находки:

* **Broken Access Control через глобальный слой памяти (приоритет №1 заказчика).** Личная просьба клиента оседает в agent_policy_memories без user_id → становится «правилом для всех клиентов» и переживает сброс сессии. В APT-цепочке «режим аудита → эксфильтрация» (CH-1) в 2 из 3 прогонов агент выдал полное досье чужого клиента: ФИО, брокерский счёт и состав портфеля — по одному невинному вопросу после подготовительной стадии.
* **Воспроизводимость.** Атаки без обращения к инструментам (фабрикация общего прошлого, флуд повторами, чужая тайна «семейным правилом») стабильны при повторах — до 9/9 активаций; флуд одним утверждением дополнительно порождает мусорные правила в глобальной политике.
* **Режим protected — не защита от отравления.** Он купирует ущерб на read-path (IAM отдаёт 403 на доступ к чужим данным), но сам вредоносный факт всё равно записывается в долговременную память в обоих режимах. Вывод для банка: память — не защищённый актив, а новая поверхность атаки; нужен контроль на write-path, а не только авторизация чтения.
* **Инфраструктура.** Попутно обнаружено, что хранилище памяти стенда (MongoDB) доступно без аутентификации — прямая запись в память минует все прикладные фильтры (аргумент за defense-in-depth).
* **Качество проверок.** Вердикт выносится в первую очередь детерминированным сканом маркеров-канареек, LLM-судья — вспомогательный (он мягче, даёт ложноположительные); согласие двух вердикторов — 89% (каппа Коэна 0.73).
