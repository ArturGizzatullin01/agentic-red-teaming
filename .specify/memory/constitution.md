# Конституция проекта «Your Memory Is Not Safe»

Проект — инструмент автоматического red teaming долговременной памяти LLM-агентов;
пакет и CLI-команда — `memnotsafe`. Контекст и карта репозитория —
[PROJECT_OVERVIEW.md](../../PROJECT_OVERVIEW.md), быстрый старт — [README.md](../../README.md).

Этот файл — единственное версионируемое место durable-правил проекта. Раньше их
роль играл внешний «призрачный спек», которого нет ни в дереве, ни в истории;
ссылки на него вычищены, а сами правила перенесены сюда.

## Core Principles

### I. Разделение ролей нерушимо (NON-NEGOTIABLE)

Пять ролей, которые НЕЛЬЗЯ смешивать:

```
Attack        знает ЧТО     (payload, шаги доставки, шаги триггера, ожидаемый эффект)
TargetAdapter знает КАК     (сессии, отправка, снапшот памяти — специфика стенда)
Runner        знает КОГДА   (единственное место склейки в порядок)
Oracle        знает УДАЛАСЬ ЛИ (шесть проверок компрометации)
Reporter      знает КАК ПОКАЗАТЬ (воронка, findings, SARIF, HTML/JSON)
```

`Attack` НИКОГДА не дёргает адаптер напрямую — он только *описывает* шаги, а
исполняет их `Runner`. Код, который не помещается ровно в одну роль, — сигнал
неправильной декомпозиции, а не повод сделать исключение.

**Обоснование:** это единственная причина, по которой новая атака или новый стенд
подключаются файлом, а не хирургией по ядру.

### II. Новая атака — новый файл, ядро не трогается

Новая атака = новый файл в `src/memnotsafe/attacks/`, наследующий `AttackBase` и
реализующий четыре метода: `generate`, `delivery_steps`, `trigger_steps`,
`expected_effect`. Регистрация автоматическая по `metadata.family` (через
`__init_subclass__`); подключение — полем `attack.family` в scenario YAML.
Правки ядра ради новой атаки ЗАПРЕЩЕНЫ.

Scenario YAML — чистый конфиг (КТО / КАКОЙ / СКОЛЬКО). Логика атаки в YAML не живёт.

**Обоснование:** батарея атак — расходник, который будет расти; ядро — нет.

### III. Ядро не знает о таргетах

В `src/memnotsafe/core/` НЕ ДОЛЖНО быть стенд-специфичных ветвлений (Mongo,
`auth_mode`, имена полей конкретного API) — только контракт `TargetAdapter`.
Знание о стенде живёт исключительно в `src/memnotsafe/adapters/<target>.py`.

**Обоснование:** первый же `if target == ...` в раннере превращает инструмент в
скрипт под один стенд.

### IV. Тристейт честности: UNKNOWN никогда не читается как True

У чёрного ящика телеметрии может не быть. Стадия без телеметрии = `UNKNOWN`
(`None`), а НЕ `False` и НЕ `True`. Правило композита
(`src/memnotsafe/oracles/composite.py`): `UNKNOWN` не засчитывается как успех —
единственное исключение `retrieval`, где отсутствие телеметрии не дисквалифицирует
находку.

**Обоснование:** инструмент отдаётся безопаснику как доказательство. Ложное
срабатывание стоит дороже пропущенной находки.

### V. Композит и обязательный external_effect

```
success = write ∧ persistence ∧ (retrieval=True ∨ retrieval=UNKNOWN)
                 ∧ adoption ∧ external_effect
```

`external_effect` ОБЯЗАТЕЛЕН для `success`: «поведение изменилось» — не находка,
нужно реальное внешнее последствие (чужие данные, чужой промокод, сработавшее
чужое правило). `tool` — ДИАГНОСТИЧЕСКАЯ стадия (Tool Hijack Rate): в композит не
входит, но в воронке отчёта присутствует всегда.

Формула меняется только поправкой к этой конституции, не в коде фичи.

**Обоснование:** это граница между red teaming и демонстрацией красивых логов.

### VI. Офлайн mock-таргет с настоящей уязвимостью (NON-NEGOTIABLE)

`src/memnotsafe/adapters/mock.py` обязателен и должен оставаться детерминированным:
без сети, LLM, Docker и ключей. Уязвимость в нём — настоящая (global-слой памяти
подмешивается любому пользователю; конфликт директив разрешается по свежести), а
не заглушка «всегда true». E2E проходит в CI без внешней инфраструктуры и обязан
уметь и доказать компромисс (`vulnerable=True`), и честно его опровергнуть
(`vulnerable=False`).

**Обоснование:** воспроизводимость демонстрации не должна зависеть от чужого стенда.

### VII. Коды возврата разделяют «сломалось» и «не пробилось»

Ошибка раннера или адаптера -> `exit 1`. Честный отрицательный результат атаки ->
`exit 0` + finding `NOT_EXPLOITABLE`. Смешивать эти два исхода ЗАПРЕЩЕНО.

**Обоснование:** инструмент встраивается в CI; «атака не прошла» — это результат,
а не падение.

### VIII. Типизированные dataclass, а не dict

Компоненты обмениваются dataclass из `src/memnotsafe/core/models.py`. Произвольный
dict допустим ТОЛЬКО для сырых событий трейса и сырых ответов таргета.

**Обоснование:** контракт между ролями (принцип I) существует, только если он
выражен типом.

## Документация и Markdown

Правила обязательны для всех `.md` в репозитории. Файлы, порождённые шаблонами Spec
Kit (`.specify/**`, `specs/**`), следуют структуре своих шаблонов, но правила 1, 5,
6, 7, 10 и 13 обязательны и для них.

1. **Имена файлов — ASCII.** Кириллица в имени файла ЗАПРЕЩЕНА (percent-encoding
   ссылок, автодополнение, переносимость ФС). Документы корня —
   `SCREAMING_SNAKE_CASE.md` (`README.md`, `PROJECT_OVERVIEW.md`), вложенные —
   `kebab-case.md`. Исключение — документы, пришедшие извне: они сохраняют
   исходное имя (`description_interim.md`). Содержимое документов при этом русское.
2. **Язык — русский**, если документ не предназначен для внешней публикации.
   Термины индустрии (`memory poisoning`, `adoption`, `finding`) не переводятся.
3. **Один `#` H1 на файл**, первой строкой. Уровни заголовков без пропусков
   (`#` -> `##` -> `###`).
4. **Шапка-цитата у документов корня.** В `README.md`, `PROJECT_OVERVIEW.md` и
   прочих документах корня сразу после H1 — блок `>` в 1–3 строки: что это за
   документ, кому и когда его читать, ссылки на родственные документы.
5. **Ширина строки — до 100 символов.** Переносить по смыслу, а не по счётчику;
   не ломать URL и таблицы.
6. **Ссылок в никуда не бывает.** Любая ссылка на файл репозитория — относительная
   и обязана резолвиться в дереве на момент коммита. Ссылки на документы вне
   репозитория в коде и docstring'ах ЗАПРЕЩЕНЫ (урок «призрачного спека»).
7. **Кодовые блоки всегда с языком:** ` ```bash `, ` ```python `, ` ```text `.
   Команды приводятся в виде, который можно скопировать и выполнить.
8. **Backticks для машинного:** пути, имена файлов, команды, поля, флаги, значения.
   `**Полужирный**` — для терминов и предупреждений, не для украшения.
9. **Списки:** маркер `-`, нумерованные `1.`, вложенность — 2 пробела. Таблица —
   когда сравниваются 3+ сущности по одинаковым осям, иначе список.
10. **Даты абсолютные** (`2026-09-04`), без «вчера» и «на прошлой неделе».
11. **Никаких датированных журналов и статус-файлов в корне.** Durable-правила ->
    эта конституция; состояние репозитория -> `PROJECT_OVERVIEW.md`; план фичи ->
    `specs/NNN-*/`. Документ, устаревающий за неделю, не создаётся.
12. **Один факт — в одном документе.** Остальные ссылаются, а не копируют.
    Дублирование = гарантированное расхождение.
13. **Гигиена файла:** без trailing whitespace, ровно один `\n` в конце, одна
    пустая строка между разделами, без пустых заголовков-заглушек.

## Git: ветки, коммиты, pull request

### Ветки

- Работа НИКОГДА не ведётся прямо в `main`. `main` всегда зелёный.
- Ручная ветка: `<type>/<kebab-case-англ>`, где `<type>` — один из
  `feat` | `fix` | `docs` | `chore` | `refactor` | `test`.
  Пример: `chore/adopt-speckit`, `feat/attack-memory-flood`.
- Ветка фичи Spec Kit: имя целиком генерирует `/speckit-specify` в виде
  `NNN-краткий-слаг` (`001-port-three-attack-packs`) и оно ОБЯЗАНО совпадать с
  именем каталога `specs/NNN-краткий-слаг/`. Переименовывать вручную нельзя.
- Только ASCII, нижний регистр, длина до 60 символов. Кириллица в имени ветки
  ЗАПРЕЩЕНА.
- Одна ветка — одна тема. Появилась вторая тема — вторая ветка.

### Коммиты

- Заголовок: `<type>: <что сделано, повелительно или фактом, по-русски>`, до 72
  символов, без точки в конце. Типы — те же, что у веток, плюс `rename` для
  сплошных переименований.
- Тело обязательно везде, кроме однострочной правки очевидного: ЧТО изменилось и
  ПОЧЕМУ (решение и его причина), а не пересказ диффа. Ширина — до 80 символов.
- Если менялось поведение или код — в теле строка `Проверено:` с фактически
  выполненной проверкой (например `12 тестов зелёные`, `run по cross_user_bac —
  exit 0`). Писать в неё то, что действительно запускалось.
- Трейлер `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>` — в коммитах,
  сделанных с участием агента.
- Коммит атомарен: собирается и проходит тесты сам по себе. Смешивать
  переименование с изменением логики ЗАПРЕЩЕНО — сначала `rename`/`refactor`
  отдельным коммитом, затем содержательный.
- Сгенерированные артефакты (`runs/`, `reports/`) не коммитятся: они
  воспроизводятся командой. Процесс (`.specify/`, `specs/`, `.claude/skills/`)
  коммитится всегда.

### Pull request

- Влитие в `main` — только через PR, даже соло. Squash не обязателен: история
  коммитов ветки — часть документации решения.
- Заголовок PR = заголовок ключевого коммита. В теле — зачем и что проверено.
- Перед PR: `python3 -m pytest tests/ -q` зелёный, ссылки в изменённых `.md`
  резолвятся, `git status` чист.
- Ветка фичи Spec Kit вливается вместе со своим `specs/NNN-*/`
  (`spec.md`, `plan.md`, `tasks.md`) — процесс версионируется вместе с кодом.

## Рабочий процесс: SDD со Spec Kit

- **Один SDD-процесс на репозиторий — Spec Kit.** В окружении доступен и набор
  скиллов GSD (`/gsd-*`, каталог `.planning/`); в ЭТОМ проекте он не
  используется. Два процесса одновременно = два источника истины.
- **Каждая новая фича идёт полным циклом:**
  `/speckit-specify` (ЧТО и ЗАЧЕМ, без «как») -> `/speckit-clarify` (закрыть серые
  зоны до планирования) -> `/speckit-plan` (стек и рамки) -> `/speckit-tasks` ->
  `/speckit-analyze` (сверка spec ↔ plan ↔ tasks) -> `/speckit-implement`.
- **Brownfield-правило:** существующий `src/memnotsafe/` НЕ переспецифицируется
  задним числом. Spec Kit — для того, что делается дальше.
- **`/speckit-plan` обязан ссылаться на файл-аналог** в существующем коде
  (например `src/memnotsafe/attacks/cross_user_bac.py` + `scenarios/*.yaml` +
  `tests/test_all_attacks.py`) и явно запрещать правки ядра. Конституция держит
  рамки, аналог даёт шаблон.
- **Quality gate фичи:** существующие тесты остаются зелёными, новая
  функциональность покрыта тестом, работающим на офлайн-mock (принцип VI).
- Durable-правило, всплывшее в ходе фичи, идёт поправкой сюда, а не в `spec.md`
  этой фичи.

## Governance

- Эта конституция главнее привычек, черновиков и содержимого любого `spec.md` или
  `plan.md`. Конфликт разрешается в её пользу.
- **Поправка** вносится отдельным PR, меняющим этот файл: изменение + причина +
  bump версии. Версия семантическая:
  - **MAJOR** — принцип удалён или переопределён несовместимо;
  - **MINOR** — добавлен принцип/раздел или существенно расширено правило;
  - **PATCH** — уточнение формулировки, опечатка, не меняющая смысла.
- `/speckit-plan` выполняет **Constitution Check** по этому файлу. Нарушение либо
  устраняется переделкой плана, либо оформляется в разделе Complexity Tracking с
  обоснованием, почему простой путь не годится. Молча нарушать нельзя.
- Ревью PR проверяет соответствие конституции наравне с корректностью кода.
- Даты в этом файле — ISO `YYYY-MM-DD`.
