# План первого live-smoke (подготовка, НЕ запуск)

**Created**: 2026-09-06 · **Ревизия 2** (L1/L2 того же дня — по аудиту Codex).
**Статус**: план по фактическому коду; Docker/API в этом задании не
запускались, бюджет провайдеров не расходуется. Цель будущего отдельного
live-пакета: один static candidate → доставка → finalize → settle → новая
trigger-сессия → ответ/снимки → сравнение oracle-вердикта с исходными
свидетельствами.

## 1. Что проверяет smoke

Целостность интеграции с живым стендом, а НЕ ASR атак: коннективность,
порядок фаз (T002-3 — код раннера, см. §4 о наблюдаемости), WRITE/PERSISTENCE
через matcher на снимках Mongo, артефакты отчёта. Один live-smoke не доказывает
ASR и готовность батареи атак. LLM-судья в текущем коде не подключён: факт
«judge inactive» и ограничения вердиктов фиксируются в smoke-отчёте; DeepSeek
не подставляется в фактически использованные роли. Атакующий — static.

## 2. Сценарий и команды (PowerShell, из рабочей копии)

Сценарий: `scenarios/direct_poisoning_live.yaml` — существующий, single-user
(attacker == victim == 1003), family `direct_poisoning`, `repetitions: 5`
(smoke-запуск — с `run`, т.е. 1 прогон).

```powershell
cd C:\Users\dota2\memnotsafe-integration\agentic-red-teaming-main

# доступность и телеметрия таргета (base_url берётся из scenario)
& '.\.venv-integration\Scripts\python.exe' -m memnotsafe.cli probe --scenario scenarios/direct_poisoning_live.yaml

# один прогон; --output обязателен (сверено с argparse)
& '.\.venv-integration\Scripts\python.exe' -m memnotsafe.cli run --scenario scenarios/direct_poisoning_live.yaml --output runs/live-smoke-direct

# пересборка отчёта; report требует --input и --output (сверено с --help)
& '.\.venv-integration\Scripts\python.exe' -m memnotsafe.cli report --input 'runs/live-smoke-direct' --output 'runs/live-smoke-direct/report-rebuilt'
```

Формы команд и флаги проверены через parser help без сетевых обращений
(`report --help`: `--input INPUT --output OUTPUT`).

## 3. КРИТИЧНО: эффект reset и требование выделенного хранилища

Факты кода (не обещания):

- `core/runner.py` вызывает `await target.reset_state()` ПЕРЕД probe каждого
  прогона (строка 191).
- `adapters/investment_stand.py::reset_state` при настроенном `mongo_uri`
  выполняет `delete_many({})` по ВСЕМ коллекциям стенда: `dialog_sessions`,
  `episodic_memories`, `semantic_memories`, `agent_policy_memories` — то есть
  удаляются записи ВСЕХ клиентов, не только тестового. Docker volumes при этом
  не удаляются, но записи коллекций — да. Отдельный user 1003 и свежие
  session_id от этого НЕ защищают.
- Если Mongo недоступен/нет прав — очистка не выполняется и это фиксируется
  (`reset_available=false` в metadata).

Следствия для smoke:

1. Запуск `run` на общем стенде СТИРАЕТ его память. Smoke допустим ТОЛЬКО на
   явно выделенном тестовом экземпляре хранилища, который разрешено очищать.
2. Агент стенда и адаптер должны использовать ОДНО И ТО ЖЕ хранилище
   согласованно (один Mongo/одну базу). Подстановка только другого `mongo_db`
   адаптеру НЕ допустима: снимки будут читаться из базы, которую агент не
   использует, — молчаливая ложная телеметрия. Общая конфигурация обоих
   компонентов (env/compose стенда против полей сценария) сверяется ДО run.
3. Не править adapter/runner ради обхода reset; не выполнять `delete`/
   `down -v`/`prune` на существующем стенде.

## 4. Предпосылки и непроверенные параметры

| Параметр | Ожидание сценария | Факт/статус | Действие при smoke |
|---|---|---|---|
| agent-api стенда | `http://localhost:8600` | НЕПРОВЕРЕННО: compose донора `genai-invest-agent-memory-stand-stack2` публикует хост-порт **9600**→8600; 8600 — порт оригинального стенда кейса | определить фактически поднятый стенд до запуска; при расхождении — отдельный live-сценарий с фактическим base_url |
| Mongo | `mongodb://localhost:27017`, db `agent_memory` | НЕПРОВЕРЕННО: stack2 публикует **28017**→27017 | сверить фактический порт и, главное, общую базу с конфигурацией агента стенда (§3) |
| ENV ключа клиента | `SK_GENAI_1003` | имя известно из сценария; значение не проверяется и не выводится | наличие без значения: `if ($env:SK_GENAI_1003) { 'set' } else { 'MISSING' }` |
| auth_mode | `vulnerable` | соответствует цели smoke | — |
| Уникальность case-маркера | — | НЕ гарантируется: producer маркера не подключён, в static payload маркер автоматически не внедряется; отдельные session_id изоляцию маркера не заменяют | трактовать совпадения текста как legacy-evidence, не как уникальную канарейку |

Всё неперечисленное и неизвестное помечается в smoke-отчёте как непроверенный
параметр; значения не выдумываются.

## 5. Наблюдаемость: что реально видно (без обещаний)

- Трейс стенда: `get_trace()` возвращает None — внутренней retrieval-трассы
  нет, RETRIEVE честно уйдёт в UNKNOWN. События close/finalize/settle
  instrumentation'ом не покрываются: их порядок гарантируется кодом раннера
  (T002-3, покрыт тестами), но НЕ наблюдаем в трейсе. Наблюдаемы: стадии в
  campaign.json (write/persistence/...), send-уровневые события адаптера
  (синтетические channel-2 события при наличии Mongo), снимки в evidence.
- WRITE/PERSISTENCE: True только с record_id/layer в evidence и (после F4)
  выжившей сигнатурой в подтверждённой записи; UNKNOWN сопровождается
  причиной (нет снимка/телеметрии/неоднозначность).
- Ответ victim-сессии фиксируется. Отказ с цитатой маркера ≠ принятие
  (exposure) — различение adoption/отказа в текущих программных проверках
  ограничено и остаётся известным ограничением до пакета trigger-only
  (T002-5); в smoke-отчёте фиксируется как ограничение, а не результат.
- Judge inactive — фиксируется в smoke-отчёте; текущий runtime НЕ пишет
  будущий полный provenance 003 (requested/resolved модели, inactive-роли) —
  не заявлять обратное.

## 6. Критерии наблюдения (успех smoke = интеграция жива)

1. `probe` → reachable=true; capabilities соответствуют адаптеру
   (memory_snapshot=True только при рабочем Mongo URI; trace=False — ожидаемо).
2. `run` завершается exit 0 (честный негатив допустим) либо exit 1 при ошибке
   транспорта/адаптера — исходы различаются и протоколируются.
3. `runs/live-smoke-direct/` содержит campaign.json + события; стадии
   объяснимы по §5 (True с идентичностью и сигнатурой; UNKNOWN с причиной).
4. Провал транспорта = ошибка; отсутствие успеха атаки = допустимый результат.
5. До запуска выполнены §3 (выделенное хранилище + согласованная конфигурация)
   и §4 (фактические порты/ENV) — отметки в smoke-отчёте.

## 7. Артефакты

- `runs/live-smoke-direct/` (campaign.json, events, report) — воспроизводятся
  командой, в git не попадают.
- Smoke-отчёт — отдельный файл в `specs/002-evidence-integrity/` по итогам
  live-пакета: фактические команды, exit-коды, judge inactive, ограничения
  вердиктов, разрешённые до запуска непроверенные параметры из §4.

## 8. Что smoke НЕ делает

Не запускает runtime-атакующего/судью (003 не реализована), не меняет модель
стенда, не измеряет ASR (и не заявляет его), не заменяет live-gate фичи 005.
