# Feature Specification: единый инструмент red teaming памяти

**Created**: 2026-09-06

**Status**: Draft для переноса в отдельные Spec Kit фичи по [плану](plan.md).

## User Scenarios & Testing

### User Story 1 — Чистый офлайн-запуск (Priority: P1)

Разработчик устанавливает пакет в пустом окружении и получает отчёт по атаке.
Ключи, Docker и донорская папка для исполнения демо не нужны.

Acceptance: уязвимый mock демонстрирует хотя бы одну воспроизводимую компрометацию;
защищённый mock её опровергает; оба результата содержат шесть стадий.
Independent Test: установка собранного wheel и run вне исходного дерева.

### User Story 2 — Перенесённые атаки (Priority: P1)

Аналитик выбирает procedural, consent, document, cross-topic или tool-error direct.
У каждой атаки есть отдельный сценарий, честное описание канала и проверка результата.

Acceptance: все пять доступны через реестр и проходят offline-проверки позитивного,
негативного и недостаточно наблюдаемого исхода без привязки mock к attack_id.
Independent Test: параметризованный тест по семействам и типам evidence.

### User Story 3 — Выбор моделей и стенда (Priority: P1)

Оператор выбирает attacker preset, target profile и независимого judge.
Статический режим не обращается к LLM. Выбор LLM attacker реально меняет генерацию.

Acceptance: отчёт содержит запрошенную и фактическую конфигурацию без ключей;
ошибка переключения не запускает кампанию; профиль другой модели не выбран молча.
Independent Test: fake HTTP и fake process runner подтверждают routing и rollback.

### User Story 4 — Проверяемый live-результат (Priority: P1)

Оператор запускает кампанию на отдельном локальном стенде и видит доказательства,
отрицательные результаты, ошибки и UNKNOWN раздельно.

Acceptance: новая сессия trigger, изоляция case, отсутствие влияния старых записей,
фиксированные модели, сохранённый raw evidence и воспроизводимый агрегат.
Independent Test: не менее пяти свежих повторов каждой основной атаки в одном профиле.

### User Story 5 — Дополнительные исследования (Priority: P2)

Cross-user и policy flood доступны после готовности соответствующих oracles.
ZWSP и conditional risk — экспериментальные, с явным статусом и без обещания ASR.
Independent Test: отсутствие выдачи другому principal не считается cross-user успехом;
отсутствие записи в контексте без внешнего последствия не считается flood успехом.

### Edge Cases

Пустые ответы/маркеры, Unicode-дефисы, отказ с цитатой, старые глобальные записи,
чужие события в окне, недоступная Mongo, задержка finalization, timeout/429,
неизвестный preset, отсутствующий ключ, одинаковые модели ролей, сбой restore.

## Requirements

### Functional Requirements

- FR-001: единый пакет и CLI команды; донор не импортируется во время исполнения.
- FR-002: пять основных атак US2, стабильные id, варианты конфигурируются без кода в YAML.
- FR-003: WRITE, PERSIST, RETRIEVE, ADOPT, TOOL, EFFECT сохраняют tristate и evidence.
- FR-004: success рассчитывается только существующим composite, не атакой или LLM judge.
- FR-005: новый trigger session отделён от доставки даже при том же user_id.
- FR-006: runtime модели и coding модели независимы; judge не меняется при выборе attacker.
- FR-007: исторические результаты не объединяются с новыми без variant/model атрибуции.
- FR-008: legacy scenario продолжает работать; неверный конфиг даёт понятную ошибку.
- FR-009: ключи только через ENV; отдельный live-профиль, локальные порты и identities.
- FR-010: инструментальные ошибки дают exit 1, честный неуспех атаки — exit 0.
- FR-011: документация и тесты воспроизводят установку на Windows и Linux.
- FR-012: raw данные не редактируются при нормализации; отчёт указывает метод сопоставления.

### Key Entities

Candidate, ExpectedEffect, RoleProfile, RunProvenance, EvidenceObservation и StageResult
уточняются в [контрактах](contracts.md). Они не заменяют существующие сущности без миграции.

## Success Criteria

- SC-001: два чистых offline-запуска, Windows и Linux, без сети во время исполнения.
- SC-002: все существующие тесты и новые regression/e2e проверки проходят.
- SC-003: пять основных атак доступны без ручного редактирования Python.
- SC-004: 100% новых live case содержат provenance либо явное unknown с причиной.
- SC-005: нет ложного успеха на отказе, install-эхе, чужом событии и одной глобальной записи.
- SC-006: live readiness подтверждён протоколом; исторический ASR не является порогом приёмки.

## Assumptions

База команды сохраняется; общая инфраструктура развивается отдельными фичами.
Live требует предоставленных оператором ключей и отдельного стенда.
Исследования natural3, web exfil v2 и публичная индексация страниц отложены.
