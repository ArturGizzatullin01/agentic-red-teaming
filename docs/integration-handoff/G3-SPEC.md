## 1. Предмет и предпосылки

### 1.1 Предмет

G3 (MASTER-PLAN §5): рубеж «до нескольких worker» — изоляция reset/global,
сверка ledger, восстановление, 1↔2 worker. P13 (MASTER-PLAN §7): worker
(после P09 full+P10b+P12+≥2 независимых slot): lease/fencing/isolation;
ступени 1→2→4; G3. Строки матрицы §6, закрываемые P13:

| Строка §6 | Что ловит | Текущий статус |
|---|---|---|
| одновременные reset/2 worker | перекрёстное загрязнение | ⬜ P13 |
| сбой после finalize до ответа | двойное завершение | 🟡 P05 / ⬜ P13 |
| исчерпание бюджета в N worker | перерасход | ⬜ P10b/P13 |

Рабочие определения (только для этого документа; закрепление — за карточками
§3, которые выдаёт владелец):

- **воркер** — один процесс кампании (CLI `run`/`campaign`) со своим
  run-каталогом `runs/<name>/`, своим `CallBudget` и своим
  `budget-ledger.jsonl`. Сегодня CLI запускает кампании последовательно;
  параллельного пути в коде нет — «два воркера» сейчас означало бы два
  независимо запущенных процесса руками одного и того же оператора;
- **ступень N** — N одновременно работающих воркеров на ОДНОМ стенде;
  ступень 4 отложена (§2 G3.5);
- **reset** в сегодняшнем коде — прямой Mongo-доступ адаптера (pymongo,
  `mongo_uri`, БД `agent_memory` по умолчанию), а не API стенда; прав на
  запись может не быть — тогда `reset_available=false` и прогон НЕ падает.

### 1.4 Главная известная дыра (W7)

W7 (MASTER-PLAN): «Нет изоляции параллельных воркеров при global
reset_state (`delete_many({})`)». Точная механика на `f4a7dcf`
(`adapters/investment_stand.py:340`): reset_state сначала сбрасывает
тристейт прогона на месте (capabilities, session_events, finalize_log,
evidence_channel), затем `delete_many({})` по ВСЕМ четырём коллекциям —
`dialog_sessions`, `episodic_memories`, `semantic_memories`,
`agent_policy_memories`; при ошибке/нет прав — `reset_available=false`,
без падения. Лечение по W7 (выбор — §4.1): разные стенды / namespace-скоуп
reset / lease-locking.

Что при этом УЖЕ работает и не должно трогаться: изоляция ПОПЫТОК внутри
одного воркера — `core/runner.py` вызывает `await target.reset_state()`
(`:221` на `f4a7dcf`; в более ранних записях планов фигурирует `:200` — до
CLOCK, удлинившего докстринг run_attack) в начале каждой попытки, а
«изоляцию держит run_id + свежие session_id»
(докстринг адаптера; session_id = `memnotsafe-{user_id}-{uuid4.hex[:8]}`).
Строка §6 «одновременные reset/2 worker» — о ПАРАЛЛЕЛЬНЫХ воркерах,
последовательные попытки не затрагивает (MASTER-PLAN, запись приёмки:
«свой reset в оснастку не добавлять»).

Глобальная коллекция одна — `agent_policy_memories` (пользовательские:
dialog_sessions, episodic_memories, semantic_memories) — она же предмет
G3.2.

## 2. Проверки гейта (G3.1–G3.5)

Формат каждой: процедура → наблюдаемые артефакты → PASS → FAIL → честный
UNKNOWN → стоп-условие. Общее для всех live-проверок: исполняются только по
«го» владельца; стенд не перезапускаем; docker logs — только read-only
диагностика при разрешении; census всегда по СЫРОМУ Mongo-снимку до любых
выводов (урок V-2).

### G3.1 Изоляция reset (одновременный reset двух воркеров)

Ловит: перекрёстное загрязнение (строка §6 «одновременные reset/2 worker»).

**Процедура.** Два воркера W1/W2 на одном stack2: разные принципалы (ключи
владельца через env, вне репо), разные run-каталоги, сценарии одного класса
(например, оба `cross_user_bac`). Шаги: (1) W1 начинает попытку — reset,
delivery (M1 записан); (2) в окне между delivery и settle W1 воркер W2
исполняет свой reset; (3) оба дорабатывают до исходов; (4) census-снимки
Mongo до/после окна, сверка с артефактами обеих кампаний. Повторить с
поменянными ролями. При включённом механизме изоляции из §3 (lease или
namespace-reset) — та же процедура против механизма.

**Артефакты.** attempts.jsonl ×2 (исходы; окно перекрытия видно по t_reset/
t_delivery/t_settle), campaign.json ×2 (`reset_available`), budget-ledger
×2, сырые Mongo-снимки (census live-оснастки), docker logs (read-only).

**PASS.** (a) Каждая попытка W1 завершается исходом, объяснимым её
СОБСТВЕННЫМ путём: либо пережила чужой reset (снимок: документы сессий W1
живы на его settle), либо стирание отчётливо атрибутировано reset-у W2
(документ удалён в окне чужого reset; у W1 — settle timeout /
NOT_EXPLOITABLE с указанием зоны/причины). (b) С механизмом изоляции:
namespace-reset W2 вообще не удаляет документы W1 (census: состав сессий W1
неизменен через reset W2), либо lease сериализует критические секции
(t_reset W2 начинается после конца критической секции W1 — видно по
timing-ам обоих).

**FAIL.** (a) Стирание опыта W1 осталось НЕатрибутированным — вердикт W1
сменился, а причина не видна в его артефактах (ложный негатив/позитив).
(b) При включённом механизме: namespace-фильтр удалил чужие документы, или
lease не удержал эксклюзивность (два reset в одном окне по timing-ам).

**UNKNOWN.** Mongo-наблюдаемость недоступна (нет `mongo_uri`, снимок
невозможен) — факт стирания ненаблюдаем; строка §6 остаётся непройденной,
никак не «пройденной».

**Стоп.** 401/403 на принципалов; порты 9600/28017 не слушают (стенд не
поднят); Mongo-наблюдаемость потеряна у ОБОИХ воркеров; в вывод попали
секреты; конфликт трёх и более воркеров одновременно (вне определения
ступени 2 — стоп, не интерпретировать).

### G3.2 Изоляция global/shared состояния

Ловит: перекрёстное загрязнение памяти между параллельными прогонами через
общую коллекцию `agent_policy_memories` и чужие слои.

**Процедура.** Параллельно на одном стенде: W1 — атака `cross_user_bac`
(флагманская пара A4), W2 — контроль `cross_user_bac_protected` (или
легитимный прогон); принципалы не пересекаются. Затем сменить роли.
Census — по сырым снимкам ДО любых выводов: где чей case-маркер (слои
user:attacker / user:victim / global), чьи записи выжили. Сверить вердикты
параллельного прогона с последовательным базисом (B0-v2).

**Артефакты.** census-таблицы (маркер × слой × бакет × воркер),
attempts.jsonl/вердикты ×2, campaign.json ×2, снимки Mongo.

**PASS.** (a) Контрольный воркер W2 не стал положительным: NOT_EXPLOITABLE,
цензус W2 чист от маркера W1. (b) Инвариант V-3C: маркер атаки — только в
бакете атакующего (user:attacker W1); global-копий нет, либо они
атрибутированы и объяснены в reason (раскладка слоёв финалайзера не
детерминирована — известный факт V-3C, требование одно: маркер НЕ в бакете
жертвы и НЕ в global без объяснения). (c) Вердикты W1 в параллели не
отличаются от последовательного базиса сверх сэмплингового шума (пин W6
записан в артефакте).

**FAIL.** Маркер W1 найден в ретриве/ответе или бакете жертвы W2; контроль
W2 стал положительным; вердикт W1 невоспроизводим из-за мусора в
global/чужих слоях.

**UNKNOWN.** Телеметрии ретрива нет (`capabilities.retrieval=false`) или
снимок недоступен — слои после delivery честно UNKNOWN; UNKNOWN ≠ False.

**Стоп.** 401/секреты/стенд — как в G3.1; заранее красный preflight
изоляции принципалов (не запускать); маркер заранее в M0 (ложная
атрибуция — стоп, менять корпус).

### G3.3 Сверка ledger (budget ledger при N=2)

Ловит: «исчерпание бюджета в N worker → перерасход» и учёт попыток без
дублей/потерь.

**Процедура.** После прогона N=2: `read_ledger` обоих `budget-ledger.jsonl`;
кросс-сверка: (1) фазы target_call — каждая запись `executed` или
`unknown_outcome` (третьего нет; `blocked` к target_call не пишется);
(2) биекция «попытка ↔ списание»: каждая строка исхода attempts.jsonl
с `attempt_no >= 1` имеет ровно одну target_call-запись с теми же
case_id/candidate_id/attempt_no — они пишутся парами в одном месте кода
(успех: executed, транспортный сбой: unknown_outcome). Строки с
`attempt_no == 0` в биекции НЕ участвуют — это `registered`
(campaign.py:227), `budget_exhausted` (:316), `aborted` (:499),
`rewrite_rejected`/`rewrite_accepted` (escalation.py:189/:210): у них нет
и не должно быть target_call. `evidence_error` (campaign.py:644, реальный
attempt_no) — легитимная ВТОРАЯ строка той же попытки, не нарушение
биекции;
(3) `retry_of`/error — поля существующей записи, повтор не создаёт второй
записи той же операции; (4) итоговая summary-запись судьи сходится с
JudgeBudget (`calls_used`, campaign.py:360), attacker-расход — с
`campaign.json.attacker.calls_used` (campaign.py:682) и считается по
записям `attacker_llm/planned` (одна на вызов, продюсер —
generation/rewrite.py:44), НЕ по общему числу строк attacker_llm:
rewrite.py пишет ДВЕ записи на вызов (:44 planned + :63 executed /
:55 unknown_outcome), planned обязан иметь парный результат; отказ
бюджета у атакера — запись `blocked` (escalation.py:162; лейджер —
наблюдатель, сам не списывает; `blocked` расходом не является); (5) суммарный расход по обоим
воркерам не превышает их суммарных бюджетов. Перерасход относительно
ОБЩЕГО бюджета эксперимента сегодня не измерим: общего лимита нет —
бюджеты (`CallBudget`, `JudgeBudget`, online_attempts) на кампанию;
judge-бюджет = 3 × repetitions × (1 + max_retries), cap `judge.max_calls`
— менять только вместе (acceptance.md). Общий лимит — §4.4.

**Артефакты.** budget-ledger.jsonl ×2, attempts.jsonl ×2, campaign.json ×2
(`budget_exhausted`), experiment.json ×2 (experiment_id, бюджеты в spec).

**PASS.** Сверки (1)–(4) сходятся по обоим воркерам; (5) без перерасхода;
дубли списаний = 0, биекция «попытка ↔ target_call» полная.

**FAIL.** target_call-запись с фазой вне {executed, unknown_outcome};
две target_call-записи на один (case_id, candidate_id, attempt_no);
нарушение биекции (попытка без target_call или target_call без попытки);
двойное списание одной операции; расхождение summary с
JudgeBudget/CallBudget; перерасход воркерного бюджета.

**UNKNOWN.** Воркер убит до summary-записи — хвост ledger без сводки
фиксируется как «сводка не завершена» (не выдумывать суммы);
`unknown_outcome` — честный третий исход, не ошибка сверки.

**Стоп.** `LedgerError` (файл невалиден) — разбор этого run-каталога
останавливается; run-каталог отсутствует/перезаписан.

### G3.4 Сбой после finalize до ответа

Ловит: «сбой после finalize до ответа → двойное завершение» (🟡 P05 /
⬜ P13).

**Процедура (только live, по «го»).** Окно между HTTP-finalize на стенде
(close_pending/finalize) и записью исхода попытки в attempts.jsonl:
(1) W1 доходит до finalize; (2) управляемый сбой воркера в окне (kill
процесса или обрыв соединения); (3) повтор попытки (эскалация/новый прогон
— тем же раннером, БЕЗ нового reset-механизма); (4) наблюдаем стенд и
учёт.

**Артефакты.** attempts.jsonl (строка сбойной попытки: transport_error,
timing отсутствует за границей сбоя — инвариант P12/CLOCK; повтор = новый
case_id и СВЕЖИЙ session_id), Mongo-снимки (число finalize-эффектов на
сессию: эпизоды не удвоены), budget-ledger (unknown_outcome у операций,
завершённых сбоем), docker logs (read-only).

**PASS.** (a) Повторная попытка создаёт новую сессию (session_id =
`memnotsafe-{user}-{uuid4…}`) — двойного завершения той же сессии нет;
(b) записи памяти не удвоены (снимок: один эпизод на finalize);
(c) вердикты честны: сбойная попытка — transport_error (не успех, не тихий
провал), разделение «потеря persist / отсутствие наблюдения» по P05
соблюдено; UNKNOWN остаётся UNKNOWN.

**FAIL.** Повторная finalize той же сессии / двойной эпизод; исход «успех»
без наблюдения; attempts.jsonl умолчал сбой.

**UNKNOWN.** Телеметрии finalize нет (P09-lite: тела finalize видны только
из ответа close_session) — эффект сбоя на стенде ненаблюдаем; фиксируется
UNKNOWN («дубля не видно» ≠ «дубля нет»).

**Стоп.** Сбой не воспроизводится управляемо (живой, не по расписанию) —
без интерпретации; секреты; для повторной попытки нужен reset стенда, а
разрешения на изолированный reset нет — стоп до «го» (норма acceptance).

### G3.5 Ступени 1→2 (→4 отложено)

Ловит: деградацию измеримости и производительности при параллелизме.

**Процедура.** (1) Зафиксировать базис ступени 1: последовательный прогон
тех же сценариев на том же стенде (свежий, либо замороженный B0-v2 —
указать в карточке); порог регресса задаётся ДО прогона (§4.8).
(2) Пустить ступень 2 (два воркера, процедура G3.1/G3.2). (3) Собрать
метрики обеих ступеней: медианы фазовых таймингов P12 на попытку
(t_reset/t_delivery/t_settle/t_trigger/t_finalize/t_scoring из
attempts.jsonl), стену и бюджетный расход (ledger summary), долю
UNKNOWN/transport_error по стадиям (stage-loss-map B4: survived/lost/
unknown + имя недостающего сигнала), вердикты/ASR против базиса (пин
сэмплинга W6 записан в артефакте — сдвиг не спишешь на температуру).
(4) Сравнить ступени по фиксированному порогу.

**Артефакты.** attempts.jsonl ×N (timing-поля), budget-ledger.jsonl ×N

Пояснения к декомпозиции:

1. **lease/fencing** — в P13-a: предложение спеки — файловый замок
   (создание O_EXCL) с TTL и монотонным fencing-токеном; устаревший
   держатель отвергается по токену. Mongo-объект как замок НЕ предлагается:
   Mongo-доступ у адаптера опционален (black-box деградация), lease не
   должен зависеть от наблюдаемости. Альтернативы фиксируются в карточке.
2. **isolation** — P13-b закрывает W7 без второго развёртывания стенда;
   «разные стенды» снимают P13-b ценой второй копии (ресурсы/решение
   владельца §4.1).
3. Ни одна offline-карточка не меняет runner, формулу, оракулы, схему
   артефактов; timing-замки offline-тестов при необходимости морозятся
   injected clock (CLOCK/CAMPAIGN-CLOCK) — норма VERDICT-P12.
4. Условие P13 «≥2 независимых slot» (§7) не расшифровано в источниках —
   §4.2; offline-часть (P13-a/b/c) от ответа не зависит, live-часть (P13-d)
   — зависит.
5. «Исчерпание бюджета в N worker» без общего лимита закрывается половиной:
   P13-c сверяет воркерные бюджеты; общий экспериментальный лимит — §4.4.

## 4. Открытые вопросы к A0/владельцу

1. **Механизм изоляции G3.1.** W7 даёт три варианта: разные стенды /
   namespace-скоуп reset / lease-locking. Спека предполагает lease (P13-a)
   + namespace-reset (P13-b) как минимум без второй копии стенда; выбор
   «разные стенды» отменяет P13-b. Решение владельца до выдачи P13-b.
2. **«≥2 независимых slot»** в условии старта P13 (§7) — не определено в
   источниках: независимые сценарии? пары принципалов? копии стенда?
   Нужно определение до live-ступени.
3. **Право сброса через Mongo.** Штатного API сброса у стенда нет; reset —
   прямой pymongo-доступ атакующей стороны к :28017 с правом записи.
   Приемлемо ли это для G3-прогонов (и не нужен ли стенду admin-эндпоинт
   сброса) — решение владельца/стороны стенда.
4. **Общий бюджет эксперимента при N worker.** Сегодня бюджеты на
   кампанию, ledger — наблюдатель; «перерасход» относительно общего лимита
   не измерим. Где живёт общий лимит (в ExperimentSpec конфигом vs
   агрегатор P13-c) — решение владельца; до решения P13-c сверяет только
   воркерные бюджеты.
5. **Ключи принципалов** для второго воркера (identities env, вне репо) —
   выдаёт владелец перед P13-d.
6. **«Го G3»** — отдельным решением после приёмки этой спеки: окно, число
   воркеров, разрешение изолированного reset — за владельцем.
7. **Хвост P05 (live 🟡).** Входит ли полное live-закрытие P05 в PASS G3.4
   или дозакрывается отдельной карточкой — решение владельца.
8. **Порог регресса G3.5.** Какой рост медианы фазы (t_settle и др.)
   считать регрессом — фиксировать в карточке P13-f ДО прогона (по
   B0-v2/P14-замеру); спека порог не назначает.
